# Arquitetura — PC Media Control

## Visão geral
```
[Celular: PWA] <--WebSocket/HTTP na LAN--> [Host no notebook (.venv Windows)]
                                              |-- WindowsProvider --> [GSMTC + Pycaw + Media Keys]
                                              |-- ChromeExtensionProvider <--WS localhost-- [Extensão Chrome MV3]
```

## Decisões iniciais e arquitetura do host
1. **Cliente = PWA servido pelo próprio host.** O celular abre uma URL local e instala na tela inicial. Funciona em Android e iOS sem loja, e evita desenvolver dois apps. App nativo fica como opção futura.
2. **Host em Python** (FastAPI + uvicorn + WebSocket), rodando nativamente no Windows via `.venv` (sem WSL) e empacotado como app de bandeja (tray) na Fase 5.
3. **Wi-Fi na mesma rede, sem servidor externo.** Bluetooth fica fora do MVP: pareamento e transporte são bem mais trabalhosos, variam por plataforma e não trazem ganho quando já há Wi-Fi.
4. **Descoberta:** mDNS/DNS-SD com `zeroconf`, publicando `_pcmedia._tcp.local.`. Como o PWA no navegador não consegue fazer mDNS por conta própria, o caminho prático é: o host mostra um **QR code** com a URL (`http://<ip>:<porta>/?pair=<token>`), filtrando adaptadores virtuais (Hyper-V/WSL) ao escolher o IP da LAN, e opcionalmente um nome `.local`. O QR também resolve o pareamento inicial.
5. **Pareamento:** QR com token de uso único (ou PIN de 6 dígitos como alternativa). Após parear, o cliente guarda um token de longa duração; o host mantém lista de dispositivos autorizados, com opção de revogar. Comandos de dispositivos não pareados são rejeitados.
6. **Provedores de sessão no host (`SessionProvider` / `PlatformAdapter`):**
   - O host mantém uma abstração de provedores de sessão e unifica todas as sessões em uma única lista, com `id` incluindo a origem (ex.: `windows:...`, `chrome:...`).
   - `WindowsProvider` (específico do Windows; espaço arquitetural preservado para `LinuxProvider`/`MacProvider` depois): lê e controla apps nativos (Spotify etc.) via GSMTC (`winrt-*`), lê e altera volume mestre/por app via Core Audio (`pycaw`) e oferece fallback via teclas de mídia globais (ex.: VLC 3.x).
   - `ChromeExtensionProvider`: recebe sessões e encaminha comandos/volume por aba vindos da extensão Chrome MV3 conectada em `localhost`.
   - **Deduplicação:** enquanto a extensão Chrome estiver conectada ao host, o host oculta as sessões GSMTC vindas de `chrome.exe` para evitar duplicatas.

## Windows: como ler e controlar mídia
- **Sessões de mídia:** GSMTC (Global System Media Transport Controls), via pacotes modulares `winrt-Windows.Media.Control` (e complementos `winrt-*`). Dá título, artista, app de origem, estado, posição e comandos (play, pause, next, previous, seek) para Spotify e apps compatíveis.
- **Volume geral e por app:** Windows Core Audio via `pycaw` (volume mestre e `ISimpleAudioVolume` por processo).
- **Fallback:** envio de teclas de mídia (play/pause, próximo, anterior, volume) quando um app não expuser sessão GSMTC (caso do VLC 3.x).

## Extensão do Chrome (MV3 — Fase 2)
- Arquitetura Manifest V3 (`minimum_chrome_version: "116"`) em `extension/` com **service worker** (`service_worker.js`, `type: module`), **content script isolado** (`content_helpers.js` + `content.js`), **ponte no mundo MAIN** (`main_world_bridge.js`) e `popup.html` de diagnóstico local.
- **ID fixo e segurança WebSocket (`Origin`):**
  - `extension/manifest.json` fixa o ID da extensão (`dcnkokmkhlcocfengaobkeacnbdjdcfa`) via campo `"key"` (chave pública RSA-2048 SPKI em Base64, gerada sem chave privada no repositório). É possível recalcular/validar o ID a partir da `"key"` usando `host.config.extension_id_from_public_key_b64(key)` (ou sobrescrever no host com `--extension-id` / `PCMEDIA_EXTENSION_ID`).
  - `/ws` valida o cabeçalho `Origin`, aceitando apenas a própria origem do host (`http://127.0.0.1:<porta>`, `http://localhost:<porta>`, `http://[::1]:<porta>` + `extra_ws_origins` na Fase 4).
  - `/ws/extension` aceita apenas Peer localhost e `Origin: chrome-extension://<ID>`.
- **Leitura de `navigator.mediaSession` (`ISOLATED` vs `MAIN` vs DOM):**
  - Pela arquitetura de *isolated worlds* do Chromium, o content script padrão (`ISOLATED`) compartilha o DOM com a página, mas possui ambiente JS isolado; além disso, sites SPA como o YouTube inicializam ou atualizam `navigator.mediaSession.metadata` no mundo `MAIN` de forma assíncrona após navegação (`yt-navigate-finish`).
  - Por isso a extensão sonda `navigator.mediaSession.metadata` no mundo `ISOLATED` (`probe.isolatedReadable`), lê o mundo `MAIN` via `main_world_bridge.js` (`window.postMessage` restrito a `window.location.origin`) e combina com **fallback/extrator DOM** (`ytd-watch-metadata`, `#channel-name`, miniaturas `i.ytimg.com/vi/<id>/hqdefault.jpg` para YouTube Watch/Shorts, YouTube Music, OpenGraph `<meta>` e `poster`/`document.title` em páginas genéricas). Em testes unitários Node e inspeção arquitetural o fluxo está validado; ao carregar no Chrome real, o popup/diagnóstico exibe em tempo real se `isolatedReadable` responde na sua versão do navegador.
- **Comportamento do Service Worker MV3 ocioso (keepalive WebSocket):**
  - No MV3, o Chrome encerra Service Workers ociosos após ~30 s; porém, desde o **Chrome 116+**, o envio/recebimento de quadros em um WebSocket aberto reinicia esse contador de inatividade.
  - O `service_worker.js` envia `{"type": "ping", "ts": ...}` a cada **20 s** (abaixo dos 30 s) esperando `{"v": 1, "type": "pong"}` do host (com timeout de 10 s para detectar socket zumbi), complementado por `chrome.alarms` (1 min) e reconexão exponencial (1 s até 15 s). Round-trip `ping`/`pong` foi validado no host e testes automatizados; confirmação de permanência > 30 s em janela ociosa real do Chrome ocorre ao carregar a extensão em `chrome://extensions`.
- Responsável por listar múltiplas abas com `<video>`/`<audio>` ou `mediaSession` (título, canal/artista, miniatura, status, posição/duração), controlar `play`/`pause`/`seek`/`±10s`/`next`/`previous`, ajustar **volume por aba** (`.volume` no elemento de mídia e silenciamento da aba via `chrome.tabs.update({ muted })`), **pular anúncio** clicando apenas no botão "Pular" visível/habilitado do YouTube (sem bloqueio de anúncios) e abrir busca do YouTube / URL (`http://`/`https://`) em nova aba.

## Protocolo (WebSocket, JSON)
Servidor -> cliente:
- `state`: lista unificada de sessões `{id, source, app, appId, title, artist, album, artworkUrl, status, position, duration, controls: {play, pause, toggle, next, previous, seek, skipAd}, volume?, muted?, isSystemActive}`, sessão ativa, volume mestre e sessões de áudio por app (`audioSessions`)
- `devices`/`error`/`pong` quando aplicável

Cliente -> servidor:
- `command`: `{sessionId, action: play|pause|toggle|next|previous|seek|seek_relative|skip_ad, value?}`
- `volume`: `{target: master|sessionId|appId, value?: 0..1, muted?: bool}`
- `select`: `{sessionId}` escolher sessão ativa
- `open`: `{mode: youtube_search|url, query?, url?}` abrir busca no YouTube ou URL `http(s)` em nova aba do Chrome
- `ping`: `{requestId?}` keepalive (responde `pong`)

Versionar o protocolo (`"v": 1`) desde o início.

## Riscos e cuidados
- Segurança na LAN: sem pareamento, qualquer dispositivo na rede controlaria o PC. Pareamento é obrigatório a partir da Fase 4 (exposição na LAN); antes disso, o host escuta só em `127.0.0.1`.
- Não expor o host fora da rede local. Sem port-forward, sem túnel.
- Adaptadores virtuais (Hyper-V/WSL/VPN) não devem ser escolhidos como IP da LAN no QR code ou no mDNS.
- Wi-Fi configurada como **Perfil Público** bloqueia conexões de entrada no Firewall do Windows; orientar mudança para **Perfil Privado** ou criação de regra para o executável/porta.
- Wi-Fi com isolamento de clientes (AP isolation, comum em redes universitárias/públicas como `172.16.x.x`) impede comunicação entre celular e notebook; documentar diagnóstico e **plano B via hotspot** (roteador Wi-Fi do notebook ou do celular).
- Chaves privadas (`.pem` de assinatura de extensão ou futuras chaves TLS) **nunca** devem entrar no repositório; caso geradas localmente, guardar fora da árvore Git (por exemplo, `%LOCALAPPDATA%\PCMediaControl\keys\`). O repositório contém apenas a chave pública SPKI no campo `"key"` do `extension/manifest.json`.
- Instalabilidade do PWA na LAN: por HTTP puro (sem HTTPS confiável no celular), navegadores Android tendem a oferecer apenas atalho na tela inicial em vez de instalação PWA completa. Incluímos `manifest.webmanifest`, ícones e `sw.js` para oferecer a melhor experiência possível em `localhost` e no celular, sem assumir instalabilidade obrigatória via HTTP.
- Risco de segurança HTTP sem TLS na LAN: o tráfego HTTP/WS na rede local trafega em texto claro, suscetível a interceptação (*eavesdropping*) ou adulteração caso a rede Wi-Fi não utilize criptografia (redes abertas). Mitigações implementadas: páginas de pareamento e teste restritas estritamente a loopback; middleware de validação do cabeçalho `Host` para mitigar ataques de DNS rebinding; validação estrita do cabeçalho `Origin` aceitando apenas a própria origem do host; armazenamento exclusivo de hashes SHA-256 dos tokens; e recomendação expressa de operar exclusivamente em redes privadas protegidas por WPA2/WPA3 ou pelo Hotspot pessoal do Windows/celular.

## Decisões
- **2026-11-11 (Fase 0) — Trocar `winsdk` pelos pacotes modulares `winrt-*`:** `winsdk` não possui distribuição compatível no PyPI para Python 3.13.1; `winrt-Windows.Media.Control`, `winrt-Windows.Media`, `winrt-Windows.Foundation` e `winrt-Windows.Foundation.Collections` (`4!10.0.28000.2957`) instalam e operam normalmente.
- **2026-11-11 (Fase 0) — Identificação e timeline GSMTC no `WindowsProvider`:** `GlobalSystemMediaTransportControlsSession` no `winrt-runtime` 4.x retorna novos objetos wrapper a cada chamada (`session == current_session` é `False`), exigindo comparação por assinatura/propriedades para identificar a sessão ativa; além disso, é necessária extrapolação por `last_updated_time` quando `PLAYING`.
- **2026-11-11 (Fase 0) — Seleção de IP da LAN deve ignorar adaptadores virtuais:** `ifaddr` retornou `Hyper-V Virtual Ethernet Adapter (172.22.96.1)` antes do Wi-Fi (`172.16.230.140`); na fase de rede/pareamento, QR code e mDNS devem filtrar adaptadores virtuais (Hyper-V/WSL) e priorizar a interface física da rota padrão.
- **2026-11-11 (Pós-Fase 0) — Hipótese de GSMTC por aba REFUTADA para múltiplas abas do YouTube:** Teste prático com 2 abas do YouTube no Chrome normal exibiu apenas 1 sessão no GSMTC (enquanto o painel nativo do Chrome lista as 2); o controle por aba do Chrome passa para uma extensão MV3 (`content script` + `service worker`, WebSocket em `localhost`).
- **2026-11-11 (Pós-Fase 0) — Volume por aba do Chrome via extensão:** Como o Core Audio agrupa todo o `chrome.exe` numa única sessão de áudio, o volume por aba será feito pela extensão (propriedade `volume` do `<video>` e/ou silenciar a aba), mantendo o `pycaw` para volume mestre e por processo.
- **2026-11-11 (Pós-Fase 0) — Abstração de provedores de sessão no host:** O host adota `SessionProvider` com `WindowsProvider` (GSMTC + Core Audio + fallback de teclas de mídia) e `ChromeExtensionProvider`, unificando sessões numa lista com `id` prefixado pela origem e ocultando sessões GSMTC de `chrome.exe` enquanto a extensão estiver conectada.
- **2026-11-11 (Pós-Fase 0) — VLC 3.x fica no fallback de teclas de mídia:** Como o VLC 3.0.23 não expõe sessão GSMTC, permanece no fallback global de teclas de mídia (sem leitura de título/seek) e com controle de volume por processo via `pycaw`.
- **2026-11-11 (Pós-Fase 0) — Ambiente nativo Windows (`.venv`) e reordenação de fases:** Projeto roda diretamente no Windows com `.venv` (sem WSL; adapter/provedor específico do Windows), e a extensão Chrome é antecipada para a Fase 2 (antes do PWA) para consolidar o controle multi-aba na base do sistema.
- **2026-11-11 (Fase 1) — Servidor `host/` em FastAPI + endpoints WS locais:** Servidor `host` (`127.0.0.1:8765`) expõe `/` (página mínima de teste), `/health`, `/api/state`, `/ws` (clientes de controle, Protocolo v1 validado com Pydantic) e `/ws/extension` (restrito a `localhost` para a extensão Chrome), com coleta de estado serializada por `asyncio.Lock` e loop de atualização ativo apenas quando há clientes conectados.
- **2026-11-11 (Fase 1) — Executor COM dedicado para Core Audio (`pycaw`):** No `WindowsProvider`, chamadas `pycaw` rodam em `ThreadPoolExecutor` de thread única inicializada com `comtypes.CoInitialize()`, evitando falhas de apartamento COM entre threads do pool padrão do `asyncio`.
- **2026-11-11 (Fase 2) — Validação estrita de `Origin` no WebSocket e ID fixo por `"key"`:** `/ws` rejeita origens fora do próprio host (preparado para `extra_ws_origins` na Fase 4) e `/ws/extension` aceita apenas `chrome-extension://<ID>`, com ID determinístico fixado pelo campo `"key"` (SPKI RSA-2048 público) em `extension/manifest.json`.
- **2026-11-11 (Fase 2) — Leitura híbrida (`ISOLATED` + `MAIN` + DOM) e keepalive MV3 de 20 s:** Content script combina sonda `ISOLATED`, ponte `world: "MAIN"` via `window.postMessage` e seletores DOM (necessários para SPA do YouTube, capas `ytimg.com` e botão "Pular"); service worker mantém a conexão ativa com `ping`/`pong` a cada 20 s (`minimum_chrome_version: "116"`) + watchdog `chrome.alarms` de 1 min.
- **2026-11-11 (Fase 2) — Extensões do Protocolo v1 para controle de abas Chrome:** Adicionados controle `skipAd` + ações `skip_ad` e `seek_relative` (`±10s`) em `command`, suporte a `ping`/`pong` em `/ws/extension`, e mensagem `open` (`youtube_search` / `url` validada em `http`/`https`) no `ChromeExtensionProvider`.
- **2026-11-12 (Pós-Fase 2) — Correção de pausa em YouTube Shorts (múltiplos `<video>` + atualização in-place):** YouTube Shorts mantém vários elementos `<video>` pré-carregados no DOM (alguns ocultos fora da viewport dentro de `ytd-reel-video-renderer`), e atualizações frequentes de `timeupdate` reconstruíam o `innerHTML` da página de teste durante o clique. A seleção do elemento em `extension/content_helpers.js` passa a pontuar `[is-active]` do reel ativo, visibilidade e viewport (além de listeners em captura e log de diagnóstico no `content.js` e `HostStateCoordinator._dispatch_command`), e `host/static/index.html` passa a atualizar slider/tempo *in-place* evitando perda do clique.
- **2026-11-12 (Fase 3) — Cliente PWA React + build estático e origem Vite isolada em `--dev`:** Cliente `client/` construído em Vite + React + TypeScript + Tailwind seguindo `DESIGN.md` (temas `auto`/`light`/`dark`, extrapolação local de posição enquanto `PLAYING`, cache inicial no `localStorage`, bottom sheet de sessões, volume mestre/aba/app, ações da extensão e manifest/ícones PNG). O host continua restrito a `127.0.0.1:8765`, serve `client/dist/` em `/` (mantendo `/legacy-test`) e só libera origens do Vite (`localhost:5173`/`127.0.0.1:5173`) quando iniciado com `--dev` (`dev_mode=True`).
- **2026-11-12 (Polimento Fase 3.1) — Resolução do glitch de reconexão de abas e normalização de títulos:** Identificada e corrigida a condição de corrida em que a inicialização do service worker disparava `sendExtensionState()` antes de as mensagens assíncronas `tab_media_state` retornarem do `content script` (o que provocava lista vazia momentânea de abas do Chrome na aba Volume). O `content script` passou a retornar o snapshot síncrono na resposta de `request_media_state`, populando imediatamente `tabStates` antes do envio. Adicionada normalização de títulos removendo prefixos de contagem de notificações (`^\(\d+\+?\)\s*`, como `(2509) `), capa em destaque amplo (estilo Apple) com ação principal de play/pause de 72 px, indicador animado de equalizador no seletor ordenando tocando primeiro, e filtragem de ruído no mixer de volume (ocultando apps inativos, sons do sistema, terminais e Chrome duplicado).
- **2026-11-12 (Fase 4) — Handshake de autenticação WebSocket no primeiro frame e tolerância a loopback:** A API padrão `new WebSocket(...)` em navegadores não permite enviar cabeçalhos HTTP customizados (`Authorization: Bearer`), e incluir o token em parâmetros de query (`?token=...`) vazaria credenciais para o histórico de navegação e logs de proxy. Adotado o handshake autenticado via primeiro frame JSON (`{"v": 1, "type": "auth", "token": "<token>"}`) dentro de uma janela de 5,0 segundos para conexões vindas da LAN (clientes em loopback são considerados de confiança local para conveniência e ferramentas de desenvolvimento).
- **2026-11-12 (Fase 4) — Pareamento de uso único, bloqueio por força bruta e store persistente em `%LOCALAPPDATA%`:** O host gera códigos de uso único de 8 caracteres alfanuméricos e PIN numérico alternativo de 6 dígitos com expiração de 5 minutos. Tentativas consecutivas inválidas disparam bloqueio temporário por 5 minutos após 5 falhas (HTTP 429). Ao concluir a troca, o host emite um token Bearer de longa duração, armazenando apenas seu hash SHA-256 no arquivo `%LOCALAPPDATA%\PCMediaControl\devices.json` (fora da árvore Git). A revogação pelo host ou cliente derruba imediatamente as conexões ativas do aparelho com close code `4001`.
- **2026-11-12 (Fase 4) — Descoberta de rede com filtro de adaptadores virtuais, mDNS e QR Code vetorial SVG:** Modo `--lan` seleciona automaticamente a interface física ativa filtrando adaptadores de virtualização e VPN (Hyper-V, WSL, VirtualBox, VMware, Tailscale, ZeroTier, Docker, etc.) e publica o serviço `_pcmedia._tcp.local.` via `zeroconf`. A renderização de QR Code na página web de pareamento (`/pair`) utiliza `qrcode.image.svg.SvgPathImage` em SVG Base64, dispensando a dependência externa de Pillow (`PIL`), e no terminal imprime em caracteres ASCII compactos.
